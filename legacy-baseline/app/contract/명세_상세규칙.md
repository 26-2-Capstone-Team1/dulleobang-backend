# 둘러방 API 명세서

버전 1.1.0 · 2026-09-30 · 모바일 / 백엔드 / AI 워커 공통 계약

## 1. 기준과 반영 범위

이번 수정의 기준은 api-spec-v1.1-changes.md입니다. 명시되지 않은 부분은 기존 v1.0 계약을 유지합니다. 사용자께서 확정하신 inputSha256 선택·미검증도 적용했습니다. 제안서와 다이어그램의 과업 문구는 자료로만 읽었으며 외부 배포 지시로 해석하지 않았습니다.

API 기본 경로는 /api/v1, 문서 버전은 1.1.0입니다. 이전 propertyType/brokerId 계약과 호환되는 별칭은 제공하지 않습니다. 모바일과 서버를 이 명세 기준으로 함께 갱신해야 합니다. 모든 예시의 example.com 주소·토큰·UUID는 설명용입니다.

| 항목 | 결정 |
|---|---|
| 추가 | 카카오·구글 로그인, 채팅, 관심매물, 신고, 소유 중개사 인증 신청 |
| 등록 권한 | 로그인 사용자 누구나 본인 매물 등록·관리 |
| 용어 | 소유 중개사 영문 ListingAgent, 역할 LISTING_AGENT; 일반 소유자 owner/ownerId |
| 유지 | 정수 원(KRW), location 객체, 기존 검색 필터, 멱등 키, ETag |
| 추천 | 별도 추천 API 없음. 홈은 GET /listings?sort=LATEST |
| 입주 상태 | 작성자 전용, 타인과 공유하지 않음 |
| 촬영 | RGB-only 유지, 실내 LiDAR 깊이·신뢰도·RoomPlan 선택 입력 추가 |
| 창문 | 중심 위치·sillHeight, 표시/가림 안내 전용, 충돌 대상 제외 |
| 충돌 보고 | inputSha256 선택, 서버 검증 없음, collisionFileSha256s 요청 입력 없음 |
| AI 형식 | 담당 확인 대기. 현재 PLY/GLB/ROOM_GEOMETRY_V1 유지 |

변경 문서에 남아 있는 영문명은 이전 사용자 요청에 따라 다음으로 통일합니다.

| 변경안 표현 | 최종 계약 |
|---|---|
| BROKER | LISTING_AGENT |
| isVerifiedBroker | isVerifiedListingAgent |
| /users/me/broker-verification | /users/me/listing-agent-verification |
| BROKER_DOCUMENT | LISTING_AGENT_DOCUMENT |
| brokerId | ownerId |

백엔드는 SQLite WAL + 로컬 파일 저장소 + 영속 outbox/큐의 단일 서버 구현입니다. 실제 AI 학습·인페인팅 알고리즘과 iOS 기기·앱 소스는 포함되지 않습니다. worker 입력 전달 및 실제 파일 검증을 구현했으며 실제 AI 품질이나 앱 무수정 연동을 보장하지 않습니다.

## 2. 공통 HTTP·인증·개인정보

HTTPS/UTF-8 JSON, lowerCamelCase, UUID, UTC RFC3339 시각을 사용합니다. 금액은 정수 원, 길이는 미터, 면적은 m²입니다. JSON NaN/Infinity·중복 키·유한 범위를 벗어난 수·미선언 필드는 거절합니다. 일반 본문 최대10MiB, 단일 객체는 직접 반환, 목록은 {items,page},204는 본문 없음입니다.

사용자 인증은 Authorization: Bearer 토큰입니다. 이메일 가입은 TENANT만 생성합니다. access15분/refresh14일, refresh 회전 및 재사용 시 해당 세션 폐기, logout 즉시 access/refresh 차단을 유지합니다. 비밀번호는 Argon2로 저장하며 토큰·비밀번호·서명 URL은 로그에 남기지 않습니다. JWT의 역할을 신뢰하지 않고 요청마다 사용자 DB 역할을 읽습니다.

카카오는 SDK accessToken을 받아 공식 token info의 app_id/회원번호/만료와 user info의 동일 회원번호를 검증합니다. 서버 KAKAO_APP_ID 설정이 필요합니다. 구글은 ID token의 RS256 공개키 서명,iss,aud,exp,iat,sub를 검증하고 GOOGLE_CLIENT_IDS 허용 목록을 사용합니다. SDK에서 받은 임의 이메일을 사용자 식별자로 사용하지 않습니다. (provider,sub)로 계정을 찾고 새 계정은 TENANT입니다. 동일 이메일의 EMAIL/KAKAO/GOOGLE 계정을 자동 병합하지 않습니다. 제공자가 이메일을 주지 않으면 User.email=null입니다.

공식 연동 기준: [카카오 REST API](https://developers.kakao.com/docs/ko/kakaologin/rest-api), [구글 OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect). 잘못된 토큰401 INVALID_OAUTH_TOKEN, 제공자 장애503 OAUTH_PROVIDER_UNAVAILABLE, 미설정503 OAUTH_NOT_CONFIGURED입니다. 실제 개발자 콘솔 앱 키/클라이언트ID를 주입해야 외부 로그인이 동작합니다.

User.authProviders는 EMAIL/KAKAO/GOOGLE 배열, phone은 선택 연락처입니다. isPhonePublic 기본 false이며 본인 PATCH /users/me로 명시적으로 동의/철회합니다. 일반 매물 소유자의 전화번호는 동의 없으면 null입니다. 소유 중개사 연락처는 운영 승인된 신청본의 사무소 번호를 사용합니다. 개인 User.phone 변경이 승인 사무소 연락처를 바꾸지 않습니다.

| 리소스 | 접근 |
|---|---|
| 매물 생성 | 모든 로그인 사용자 |
| 매물 수정·삭제·게시·촬영·객체 분류 | 해당 매물 소유자 |
| 공개 매물·원본 공간·정제 사진 | 로그인 사용자 |
| 비공개 매물 | 소유자만 |
| 상세 주소 location.detailAddress | 상세 조회 소유자만, 목록·채팅에는 항상 생략 |
| 개인 가구·촬영·작업·인증 서류 | 소유자만 |
| 입주 상태·제거 결과·배치 | 작성자이며 현재 매물 접근권한도 필요 |
| 채팅·읽음·메시지 | 참여자 두 명만 |
| 워커 | 별도 AI_WORKER JWT + 현재 lease |

권한 없는 특정 리소스는404로 숨깁니다. 인증표시 true는 서버 LISTING_AGENT 역할로 계산합니다. 역할을 직접 넣는 가입/수정 요청은422입니다. 사무소 이름·번호는 승인본이 없으면 null이며 증빙/등록번호는 매물 응답에 나오지 않습니다.

## 3. 멱등·ETag·파일 주소

생성·촬영 제출·입주 상태·재시도·refresh·인증 신청·신고·채팅 개설/전송은 선언된 API의 UUID Idempotency-Key를 사용합니다. 범위는 사용자+method+실제path+key,유효24시간입니다. 같은 키·같은 JSON은 최초 상태코드/본문을 재생하고 다른 내용409 IDEMPOTENCY_KEY_REUSED입니다. 로그인 세션·소유권을 재생 전 다시 검사합니다. SQLite 동시 요청은 트랜잭션 잠금으로 기다린 뒤 재생하며 잠금 장애는503입니다. 생성·메시지 부수효과는 한 번만 수행합니다.

AssetRef의 url/urlExpiresAt은 응답 때 새로 채우는 파생값으로 파일 바이트/sha256/버전에 영향을 주지 않습니다. 멱등 응답에서도 파일 GET 주소는 현재 시점으로 재발급합니다. 업로드 PUT URL은 기존 응답을 재생하며 만료하면 upload-urls로 갱신합니다. 모든 파일 참조를 담은 목록·상세·공간·입주상태·가구 응답에 즉시 사용 가능한15분GET URL을 제공합니다. URL의 Authorization 헤더는 보내지 않습니다. 만료/403이면 GET /assets/{fileId}/download로 갱신합니다. download 요청 자체는 사용자 Bearer 토큰이 필요합니다.

변경 API는 강한 ETag: "3"과 If-Match: "3"를 사용합니다. 누락428,불일치412 VERSION_MISMATCH입니다. 배치 첫PUT은 If-None-Match:*; 이미 있으면412. 두 조건 헤더 동시 전송400입니다. AI 완료 등 서버가 현재 포인터/상태를 바꾸어도 메타데이터 version이 증가하므로 수정 전 최신GET을 사용합니다. 삭제 재요청은 소유권 tombstone30일 동안204를 유지합니다.

다운로드 주소가 공유되면 만료까지 사용 가능하므로 영구 저장·로그하지 않습니다. immutable AssetRef의 다섯 필드만 워커 결과 계약의 기준입니다. worker complete 입력에서 url/urlExpiresAt은 검증 대상 파일 메타데이터가 아니며 새 주소를 영구 에셋 식별자로 쓰지 않습니다.

## 4. 매물·목록·검색

ListingCreate 필수는 roomType,price,location,exclusiveAreaM2,rentalOptions입니다. title/description/floor와 앱 추가필드는 선택입니다. 서버가 제목을 만들어 저장하지 않으며 앱이 지역명·방종류로 표시 문구를 구성합니다. floor 생략이면null. price는 leaseType MONTHLY/JEONSE,deposit,monthlyRent,maintenanceFee,currency KRW입니다. 월세는 monthlyRent>=1,전세는0,관리비null은협의입니다. 앱이 원↔만원을 변환합니다.

roomType은 ONE_ROOM/TWO_ROOM/THREE_ROOM/OFFICETEL입니다. 총층totalFloors,공급면적supplyAreaM2,방수roomCount,욕실수bathroomCount,입주availableFrom(IMMEDIATE 또는YYYY-MM-DD),생활설명livingEnvironment(0~500자)를 추가합니다. 공급면적은 전용면적 이상,층은 총층 이하입니다. 기존10옵션+PARKING/PET_ALLOWED/ELEVATOR를 UPPER_SNAKE_CASE로 받습니다. 배열중복은 금지합니다. PATCH의price/location은 전체객체교체이므로 누락주소 필드를 부분 업데이트하는 방식으로 보내지 않습니다.

Listing.owner는 userId/displayName/isVerifiedListingAgent/officeName/phone입니다. ownerId는 서버 결정입니다. ListingSummary.owner는 앞의3필드만 제공합니다. Summary의roomType/floor/price.maintenanceFee/location/exclusiveAreaM2/thumbnail.url/hasSpace/isScrapped로 목록 카드를 그립니다. 일반 소유자·소유 중개사 모두 본인 매물을 관리할 수 있습니다.

q는 저장한 공개 roadAddress의 공백 단어별AND,대소문자무시부분일치입니다. 주소 문자열에 동·지번이 있으면 검색되지만 별도 지오코딩/지번변환은 하지 않습니다. 방종류 자연어는 앱이 roomType 필터로 옮깁니다. regionCode는 선택 정확일치입니다. roomType 반복값은OR,옵션 반복값은모두포함AND,범위는양끝포함입니다. 원래minDeposit/maxDeposit/minMonthlyRent/maxMonthlyRent/minAreaM2/maxAreaM2/leaseType/hasSpace/sort를 유지합니다. minPrice/maxPrice/location 같은 미선언 query는400입니다.

지도minLat/maxLat/minLng/maxLng는네개모두필요(부분400),역전422입니다. 일반limit기본20/최대50,네지도경계포함시최대200입니다. 날짜변경선을 넘는 bbox는 지원하지 않습니다. 커서는 호출자·경로·필터·정렬에 묶인30분서명토큰이며 서버의ID스냅샷을 순회합니다. 필터변경/만료400 INVALID_CURSOR. 값수정은최신값이므로 전체DB시점스냅샷은아닙니다. 빈목록은200 items=[]입니다.

게시 조건은 이전과 같이 완성 공간+사진1장이상이며 자동 게시하지 않습니다. DRAFT↔PUBLISHED,둘다ARCHIVED,ARCHIVED→DRAFT입니다. ARCHIVED전환은활성작업이있으면409입니다. 기존 VILLA/APARTMENT는 자동으로 방수를 알 수 없어 DRAFT로 이동하고 소유자가roomType을 확인한 뒤 게시합니다. 이때 ROOM_TYPE_REVIEW_REQUIRED 오류로 확인을 요구합니다.

## 5. 관심매물·신고·인증·채팅

PUT /listings/{listingId}/scrap은 이미 담겨 있어도 204이며 최초 savedAt을 유지합니다. DELETE도 기록이 없어도 204입니다. 삭제·비공개 매물의 관심 기록도 해제할 수 있습니다. GET /users/me/scraps는 최근 담은 순서의 ListingPage를 반환하고 공개 중인 매물만 보여 줍니다. 숨겨진 관심 기록은 유지합니다. isScrapped는 요청자별 응답값입니다.

신고 POST는 reason(FAKE_LISTING, SPACE_MISMATCH, WRONG_PRICE, ALREADY_CONTRACTED, OTHER), 선택 detail(0~1000자)을 받습니다. 최초 201 {reportId}; 동일 사용자·매물의 24시간 내 재신고는 처리 상태·사유와 무관하게 200으로 기존 ID를 반환합니다. 같은 Idempotency-Key는 최초 201을 재생합니다. 본인 매물 신고는 403입니다. 상세 신고 내용은 일반 사용자에게 공개하지 않고 운영 CLI에서 검토합니다.

인증은 GET/POST /users/me/listing-agent-verification입니다. 상태는 NONE → PENDING → APPROVED/REJECTED입니다. name, licenseNumber, officeName, phone, documentFileId를 보냅니다. 먼저 USER=본인, LISTING_AGENT_DOCUMENT 목적의 JPEG/PNG 정확히 1장을 업로드·complete해야 합니다. PENDING 중 새 신청은 409 VERIFICATION_PENDING, 반려 후 재신청은 허용합니다. 운영자는 pending-reviews 및 review-agent CLI로 자격을 확인합니다. 승인 시에만 LISTING_AGENT 역할을 부여하며 클라이언트 자가 승격은 없습니다.

POST /chats {listingId}는 최초 201, 같은 매물·문의자의 기존 방은 200입니다. 소유자가 자기 매물의 방을 만들면 409입니다. 문의 상대는 인증 여부와 무관한 매물 소유자입니다. GET 목록은 최신 메시지 순서(메시지 없으면 생성 순서), 상대 요약·목록 카드·lastMessage 문자열/null·lastMessageAt·unreadCount를 반환합니다. GET /chats/{id}는 inquirerId, ownerId, createdAt, readOnly를 추가합니다.

메시지 POST는 text 1~1000자와 Idempotency-Key가 필수이며 201입니다. 공백뿐인 본문은 422입니다. GET 메시지는 최신부터, page 커서 또는 before=<동일 방 messageId>의 배타적 상한으로 이전 기록을 읽습니다. before와 cursor를 함께 쓸 때 최초 before/limit를 동일하게 유지합니다. 읽음 요청은 lastReadMessageId로 같은 방 메시지임을 확인하고 읽음 위치를 감소시키지 않습니다. unreadCount는 타인 메시지 중 읽음 위치 뒤의 수입니다. 읽음 요청은 204이며 새 메시지 전송 시 채팅 목록 정렬 시각이 갱신됩니다.

매물 삭제·보관·비공개 이후에는 기존 대화만 읽을 수 있고 새 전송은 409 CHAT_LISTING_UNAVAILABLE입니다. 채팅 목록 카드는 공개 당시의 민감 주소 없는 스냅샷으로 보존하며 비공개·삭제 이후에는 사진 URL을 제공하지 않습니다. 제삼자 조회는 404입니다. 앱은 화면이 열린 동안 3~5초마다 폴링합니다. WebSocket/SSE·푸시·첨부는 이번 범위에 포함하지 않습니다.

## 6. 업로드·카메라·깊이·RoomPlan

대상 생성 → clientFileId/바이트 크기/SHA-256 계산 → upload-sessions → 파일별 서명 PUT(지정 Content-Type/x-amz-checksum-sha256) → complete 검증 → captures에 uploadSessionId 제출 → 202 jobId → 작업 폴링 순서입니다. capture 본문에 바이너리/Base64를 넣지 않습니다. 사진은 VERIFIED 업로드 파일 ID를 PATCH photoFileIds로 연결하며 촬영과 용도를 교차할 수 없습니다. 검증 이후 PUT은 불변입니다.

| 목적 / role | 수와 형식 |
|---|---|
| ROOM_CAPTURE IMAGE | JPEG/PNG RGB 30~1000 |
| FURNITURE_CAPTURE IMAGE | JPEG/PNG RGB 12~300, 기존 RGB 방식 |
| CAMERA_MANIFEST | camera.json 정확히 1 |
| ROOM_CAPTURE DEPTH | PNG 단일 채널 uint16 mm, 0=무효; 0 또는 IMAGE 수 |
| ROOM_CAPTURE CONFIDENCE | PNG 단일 채널 uint8, 0/1/2; 0 또는 IMAGE 수, DEPTH 없이 금지 |
| ROOMPLAN | Apple CapturedRoom JSON 0~1 |
| ROOMPLAN_STRUCTURE | 정규화 RoomPlanStructure JSON 0~1 |
| LISTING_PHOTO | JPEG/PNG 1~20 |
| LISTING_AGENT_DOCUMENT | 본인 USER JPEG/PNG 1 |

role 생략 시 목적/MIME으로 기존 IMAGE/CAMERA_MANIFEST/사진/서류만 추론합니다. 깊이·RoomPlan은 role을 명시합니다. 이미지 20 MiB/JSON 10 MiB/세션 5 GiB, RGB와 증빙은 640×480 이상·각 축 8192 이하·40M 픽셀 이하입니다. 깊이·신뢰도는 각 축 1~4096이며 PNG signature/IHDR bit depth·실제 디코드·해상도를 확인합니다. 세션 24시간/서명 URL 15분입니다. 실내 추가 입력을 가구 세션에 혼용하지 않습니다.

CameraFrame의 depthClientFileId/depthWidthPx/depthHeightPx는 함께 제공합니다. confidenceClientFileId는 depth가 있고 같은 해상도일 때만 가능합니다. 모든 depth/confidence 파일은 프레임에서 정확히 한 번 참조해야 합니다. 미참조·중복·누락·역할 혼용·해상도 불일치는 422입니다. RGB 프레임 집합·시각·pose·K도 검증합니다. 깊이 K는 fx/cx에 depthWidthPx/widthPx, fy/cy에 depthHeightPx/heightPx를 곱합니다. 두 비율이 같은 기기에서는 변경안의 단일 비율식과 같습니다.

ReconstructionInput은 manifest/images와 depths/confidences DownloadGrant 배열, roomplan/roomplanStructure DownloadGrant|null을 가집니다. DownloadGrant.clientFileId로 camera.json의 이미지·깊이 참조와 다운로드 fileId를 연결합니다. LiDAR 없는 기기는 RGB+camera만 보내며 워커는 추가 입력의 빈 배열/null을 받습니다.

Apple 원본 RoomPlan JSON과 앱 추출 RoomPlanStructure는 다릅니다. 원본은 walls/doors/windows/objects 배열을 가진 CapturedRoom 데이터로 보존합니다. 정규화 구조는 schemaVersion 1.0, coordinateSystem RH_Y_UP_Z_BACK, unit METER, surfaces/objects이며 표면·객체는 중심 transform와 dimensions를 가집니다. 임의 파일을 자동 변환하지 않고 앱이 이 명시 계약으로 변환합니다. 구조 파일은 cameraToWorld와 같은 월드 좌표입니다. 원본 RoomPlan의 원점이 다르면 roomPlanToWorld(열 우선 강체 변환)를 제공하고 워커가 원본에만 한 번 적용합니다.

CameraManifest는 ARKit/ARCore, 열 우선 4×4 cameraToWorld, 미터, 바닥 기준 원점입니다. timestampUs는 세션 시작부터 단조 증가 마이크로초이며 trackingState NORMAL만 제출합니다. 왜곡 보정·EXIF 방향이 반영된 RGB와 해당 해상도의 intrinsics를 사용합니다. fx/fy>0, 0≤cx<width, 0≤cy<height입니다. translation은 index 12/13/14, 마지막 행은 0/0/0/1, R 직교와 det+1 허용 오차는 1e-3입니다. 추적 원점이 reset되면 새 세션을 촬영합니다. 단일 AR 세션의 공통 좌표계를 유지해야 합니다.

## 7. 3D 좌표·결과 파일·창문

### 7.1 좌표와 Unity 변환

모든 API의 position, dimensions, boundingBox, geometry, collision GLB는 미터 단위 오른손 좌표계입니다. X 오른쪽, Y 위, -Z 전방이며 Euler angle을 사용하지 않습니다. rotation은 quaternion {x,y,z,w}, 길이 오차 1e-4 이하입니다. 가구는 local pivot이 바닥 중심이고 dimensions=(width,height,depth)는 회전 전 로컬 크기입니다. boundingBox.min=(-w/2,0,-d/2), max=(w/2,h,d/2)를 0.001m 오차 안에서 만족합니다. 가구 scale 변경 필드는 없습니다.

Unity의 +Z 전방 좌표로 변환할 때 pUnity=(x,y,-z), qUnity=(-qx,-qy,qz,qw)를 사용합니다. 행렬은 H×M×H, H=diag(1,1,-1,1)입니다. 정점·법선의 z 부호를 반전하고 삼각형 winding을 반전합니다. GLB importer가 이미 좌표계를 변환하는 경우 추가 반전하지 않습니다. 변환은 데이터 경계에서 정확히 한 번 적용합니다. q와 -q는 같은 회전이므로 비교 전 w≥0으로 정규화하고 w=0이면 첫 비영 성분을 양수로 정규화합니다.

방 floorPolygon은 [x,z] 배열이며 마지막 점을 반복하지 않는 단순 다각형입니다. +Y에서 내려다볼 때 반시계로 정의하고 자기 교차를 거절합니다. ceilingY>floorY이며 areaM2는 해당 바닥 다각형의 면적과 0.01m² 오차 내 일치해야 합니다. 다중 room은 동일 층·공통 원점에 배치합니다. roomDimensions는 전체 공간의 월드 AABB 크기이고 registered exclusiveAreaM2와 다릅니다.

### 7.2 에셋 형식

AssetRef는 fileId, contentType, byteSize, sha256, format을 가진 불변 참조입니다. 공개 응답에 s3:// 키나 외부 임의 URI를 넣지 않습니다. 각 응답에서 url과 urlExpiresAt을 제공하고 download API도 권한 검사 후 재발급합니다. URL 만료는 데이터 삭제가 아니며 같은 fileId로 갱신합니다. 클라이언트는 SHA-256으로 로컬 캐시를 식별하고 다운로드 바이트를 검증합니다. 서명 URL 유출 시 만료까지 접근 가능하므로 URL을 영구 저장·로그하지 않습니다.

| role / 필드 | format / MIME | 요구 조건 |
|---|---|---|
| sceneAsset | DULLEOBANG_GS_PLY_V1 / application/octet-stream | 아래 고정 3DGS 프로파일, visual 전용 |
| geometryAsset | ROOM_GEOMETRY_V1 / application/json | RoomGeometry와 정확히 같은 내용 |
| collisionAsset | GLB_V2 / model/gltf-binary | 삼각형 mesh, collider node 이름으로 매핑 |
| modelAsset | GLB_V2 / model/gltf-binary | 가구 visual mesh, 단위·pivot bake |
| 사진 | JPEG 또는 PNG / image/jpeg 또는 image/png | EXIF 위치·기기 식별 정보 제거 후 공개 |
| 카메라 파일 | CAMERA_JSON_V1 / application/json | CameraManifest, 소유자·워커 전용 |

공개 사진은 업로드 원본을 변형하지 않고 EXIF 제거된 별도 파생 AssetRef를 발급합니다. ListingPatch.photoFileIds는 검증된 업로드 파일을 받되 Listing.photos에는 이 파생 파일 참조가 반환됩니다. 해당 파생 생성 실패 시 사진 연결을 실패시키고 기존 사진 배열을 유지합니다.

DULLEOBANG_GS_PLY_V1은 본 프로젝트에서 선택한 인터페이스이며 모든 3DGS 라이브러리가 자동 지원한다는 뜻이 아닙니다. binary_little_endian PLY 1.0, vertex N, face 없음, SH degree 0으로 제한합니다. vertex당 float32 14개를 x,y,z,f_dc_0,f_dc_1,f_dc_2,opacity,scale_0,scale_1,scale_2,rot_0,rot_1,rot_2,rot_3 순서로 저장합니다. rot는 이 파일 안에서만 [w,x,y,z]이며 API quaternion과 순서가 다릅니다. alpha=sigmoid(opacity), 각 축 표준편차[m]=exp(scale_i), 선형 RGB=clamp(0.5+0.28209479177387814×f_dc_i,0,1)입니다. rotation은 단위 quaternion, vertex 좌표는 API 월드 좌표입니다. normals/f_rest/압축 확장/추가 필드는 v1에서 사용하지 않습니다. 댓글 헤더 comment dulleobang_gs_ply_v1을 포함합니다. 최대 2,000,000 splat, scene 파일 최대 256 MiB로 제한합니다. 이 선택은 렌더러 연동을 명확히 하기 위한 기준안이며 품질 평가에 따라 새 format 버전으로 확장할 수 있습니다.

GLB는 glTF 2.0 단일 바이너리이며 외부 버퍼·외부 이미지 URI, 압축 확장, 스킨·애니메이션을 허용하지 않습니다. 모델 texture는 GLB 내부 PNG/JPEG, local 축과 실제 크기를 bake하고 루트 transform은 identity입니다. collision 파일은 texture 없이 TRIANGLES primitive를 사용하고 전체 합 200,000 triangle 이하입니다. model GLB는 256 MiB, collision GLB는 64 MiB, geometry JSON은 10 MiB 이하입니다. glTF의 기반 형식은 공식 규격을 따르며 이 제한은 프로젝트 프로파일입니다. [glTF 2.0 규격](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html)

충돌 GLB는 구조물별 node, 기존 객체별 collisionNode, 문 개폐 영역별 sweepNode를 가집니다. node name은 파일 내 유일하고 참조된 이름은 실제 존재해야 합니다. 구조물·문 node는 월드 좌표에 bake하고, 객체 node도 월드 좌표에 bake하므로 SpaceObject.transform을 다시 적용하지 않습니다. 가구 collision GLB만 로컬 좌표로 보존하며 PlacementItem.transform을 적용합니다. 기존 객체 제거 결과는 해당 node를 삭제하고 bundle.objects에서 같은 objectId를 제외합니다. 구조물 ID·좌표·문 ID와 나머지 객체 ID는 원본과 동일하게 유지합니다.



창문은 RoomGeometry.windows 0~200개이며 과거 파일의 생략은 정보 없음으로 읽습니다. windowId, roomId, transform, width, height, sillHeight를 사용합니다. position은 창 중심이며 중심 Y=floorY+sillHeight+height/2(허용 1mm), 상단은 ceilingY 이하입니다. Y축 방향 회전의 단위 quaternion과 양수 너비/높이를 사용합니다. collisionNode·충돌 kind를 갖지 않으며 가림 안내용입니다. 제거 결과에서도 구조·문·창문을 보존합니다.

충돌 참고 보고는 rulesVersion/evaluatedAt/isPlaceable/collisions를 검사하고 inputSha256은 선택이며 재계산하지 않습니다. checksum 배열 입력을 받지 않습니다. 모바일은 벽·가구 상자로 계산할 수 있고 서버는 정밀 물리 검사를 수행하지 않습니다. CLIENT_ONLY로 저장하며 충돌이 있는 배치도 저장할 수 있습니다. 충돌 내용과 isPlaceable의 구조적 일치·placement 참조·시각 형식은 검증합니다. 실제 배치 가능성이나 계약 가능성 판단이 아닙니다.

## 8. 비동기 작업·개인 상태·배치

모바일은 워커에 직접 접근하지 않습니다. 큐는 at-least-once 전송을 가정하며 Job 테이블이 상태의 기준입니다. API 서버는 Job과 outbox를 같은 트랜잭션으로 저장한 뒤 202를 반환합니다. outbox dispatcher가 QueueMessage를 전송합니다. 일시 큐 장애는 outbox 재전송으로 복구하며 접수된 작업을 잃지 않습니다. 큐 메시지에 서명 URL·사용자 토큰·임의 입력 URL은 넣지 않습니다.

워커는 메시지 jobId로 claim합니다. 서버는 실행 가능 여부 확인, attemptNo 증가, RUNNING 전환, 120초 lease 발급을 원자 처리합니다. 동일 job에 한 워커만 유효 lease를 가집니다. 30초 heartbeat가 lease를 120초 연장하고, 상태·진행률을 저장합니다. 워커 실행 제한은 attempt당 30분이며 heartbeat로 무한 연장하지 않습니다. 대기 60분 초과 작업은 QUEUE_TIMEOUT 상황을 INTERNAL_ERROR, retryable=true로 실패 처리하고 error.message에 만료 원인을 기록합니다.

| 상황 | 서버 처리 |
|---|---|
| 중복 큐 메시지 | claim 시 RUNNING/종료이면 409; 상태 확인 후 메시지 ack |
| 워커 중단·lease 만료 | WORKER_TIMEOUT, 잔여 attempt가 있으면 RETRY_WAIT |
| 자동 재시도 | 총 3 attempt. 1회 실패 후 10초, 2회 후 30초 대기 |
| 자동 재시도 허용 | WORKER_TIMEOUT, DEPENDENCY_UNAVAILABLE, INTERNAL_ERROR |
| 영구 입력/산출물 오류 | INSUFFICIENT_FRAMES, TRACKING_UNSTABLE, SCALE_UNRELIABLE, INVALID_ARTIFACT 등은 FAILED |
| 수동 재시도 | FAILED + retryable=true만 새 jobId. 기존 실패 이력 유지 |
| 취소와 완료 경합 | Job 행 잠금으로 먼저 커밋된 전이가 승리 |
| 오래된 결과 | 현재 attempt/lease가 아니면 409 JOB_LEASE_LOST |

재시도 stage/progress는 새 attempt에서 초기화될 수 있으므로 앱은 attemptNo를 함께 표시합니다. RUNNING progress는 0~99, COMPLETED만 100입니다. QUEUED/RETRY_WAIT pollAfterSeconds=3, 종료는 0입니다. COMPLETED는 result!=null, error=null, finishedAt!=null; FAILED는 result=null, error!=null, finishedAt!=null; CANCELED는 result=null, error=null, finishedAt!=null입니다. RETRY_WAIT는 최근 error를 보존하고 finishedAt=null입니다.

result 매핑은 ROOM_RECONSTRUCTION → SPACE(resourceId=listingId, version=spaceVersion), FURNITURE_RECONSTRUCTION → FURNITURE_MODEL(resourceId=furnitureId, version=modelVersion), ROOM_OBJECT_REMOVAL → ROOM_STATE(resourceId=roomStateId, version=1)입니다. ROOM_OBJECT_REMOVAL Job.targetType은 ROOM_STATE, targetId는 roomStateId입니다.

워커는 artifacts에 필요한 파일 메타데이터를 등록하고 받은 fileId/PUT URL로 저장합니다. 같은 attempt/clientFileId와 동일 내용으로 재호출하면 동일 fileId 및 새 URL을 반환합니다. complete에는 이 fileId의 AssetRef만 사용할 수 있습니다. 서버는 역할별 형식·byteSize·checksum·소유 job/attempt를 검사하고, geometryAsset JSON과 bundle.geometry의 구조적 동등성, 객체·문·collider 참조, 치수·좌표 규칙을 검증합니다. 완료 응답 전에 파일 검증과 DB 변경을 끝냅니다. 파일 검증 중 lease 만료도 최종 커밋 때 재검사합니다.

원본 공간 복원 시 객체 ownershipType은 모두 UNKNOWN으로 시작합니다. 가구 실측치가 제공되면 복원 모델에 균일 스케일만 적용하고 축별 비율 차이가 5%를 넘으면 SCALE_UNRELIABLE로 실패시킵니다. 이는 프로젝트 품질 기준이며 실측 정확도 보장이 아닙니다. 실측치가 없으면 AR tracking 기반 스케일을 사용합니다.

제거 결과는 요청 removedObjectIds 집합과 정확히 일치해야 합니다. 남은 객체는 원본 객체 집합에서 제거 집합을 뺀 것과 같아야 하며, 원본 좌표·room·door·window·structural collider를 유지합니다. 새 임의 객체를 추가할 수 없습니다. 시각화 inpainting은 추정 영역이므로 quality.warnings에 INPAINTED_REGION을 포함합니다.

성공 완료 callback의 같은 lease/동일 body는 200으로 재생하고, 다른 body는 409 CALLBACK_CONFLICT입니다. 이 재생은 이미 성공한 lease에 한해서만 만료 이후에도 허용합니다. fail도 같은 규칙으로 중복 보고를 재생하되 현재 상태를 되돌리지 않습니다. 워커는 완료/실패가 DB에 반영되었거나 종료 상태임을 확인한 후 큐 ack합니다. 현재 DB 영속 큐는 별도 visibility timeout 없이 Job lease를 사용합니다. scheduler가 만료·재시도 시각을 관찰해 재큐잉하므로 큐 메시지 유실에 의존하지 않습니다.



저장 배치는 (userId,listingId)에 대해 1개입니다. 여러 개 배치안·공유 링크는 v1에 포함하지 않습니다. 사용자가 다른 매물에 같은 가구를 사용하는 것은 허용하며, 같은 배치 안에 동일 furnitureId를 2회 넣는 것은 거절합니다. placementId도 세트 안에서 유일해야 합니다. furnitureId는 반드시 본인 소유이며 지정 modelVersion의 완성 모델이 존재해야 합니다.

ORIGINAL이면 roomStateId=null, ROOM_STATE이면 본인 READY 상태 ID가 필요합니다. 상태 listingId 및 sourceSpaceVersion이 저장 요청과 일치해야 합니다. 현재 매물 공간과 다른 spaceVersion 또는 현재 가구 모델과 다른 modelVersion으로 새로 저장하면 409를 반환합니다. 기존 배치는 과거 불변 버전을 계속 조회할 수 있지만 isStale=true를 표시하고, 앱은 새 기준을 불러와 배치를 재검토한 뒤 저장합니다. 자동 좌표 전환은 하지 않습니다.

다른 매물 비교는 getMyPlacements와 각 매물/공간/동일 가구 데이터를 조회해 앱에서 구성합니다. 공간이 다른데 원래 position을 그대로 복사한 결과를 유효 배치로 취급하지 않습니다. furnitureId는 재사용하고 매물마다 transform을 별도 저장합니다.

가구 및 입주 상태는 저장 배치가 참조하면 삭제를 409 RESOURCE_IN_USE로 막습니다. 사용자는 먼저 해당 배치에서 참조를 제거하거나 배치 세트를 삭제해야 합니다. 매물 삭제는 상위 비노출을 우선하며 관련 작업을 취소하고 하위 공간·상태·배치를 접근 차단합니다. ARCHIVED는 삭제가 아니라 매물 소유자용 보관 상태이고 임차인에게는 보이지 않습니다. ARCHIVED를 DRAFT로 되돌린 뒤 다시 게시할 수 있습니다.

완성된 공간·모델의 과거 버전은 상위 리소스가 존재하는 동안 유지합니다. 원본 캡처는 마지막 관련 Job 종료 후 30일 유지하며 활성 작업이 참조 중이면 정리하지 않습니다. 만료 후 수동 재시도는 410 INPUT_EXPIRED로 재촬영을 안내합니다. 삭제 권한 차단은 즉시 적용하고 불필요 파일은 유지관리에서 정리하며 tombstone은 최소 30일 유지합니다. 이는 v1 저장 운영 정책입니다.



입주 상태는 작성자만 조회하며 소유 중개사가 만들어도 임차인 전체에 공개하지 않습니다. 매물 소유자가 객체를 PERSONAL/RENTAL_OPTION/UNKNOWN으로 분류하고 PERSONAL+removable=true만 제거합니다. 최초 AI 객체는 UNKNOWN입니다. ROOM_STATE 배치는 본인 READY 상태만 선택합니다.

배치 isStale는 저장된 spaceVersion/modelVersion과 현재 버전 차이로 결정합니다. 메타데이터 ETag와 아티팩트 버전은 다릅니다. inputSha256의 유무·맞고 틀림이 isStale나 저장 성공을 바꾸지 않습니다. 배치 전체 PUT·참조 중 삭제 409·사용자별 격리는 기존 규칙을 유지합니다.

## 9. 실패 복구·검증 범위

오류는 RFC 9457 application/problem+json/code/requestId입니다. 400 입력·query·cursor, 401 토큰, 403 기능 권한, 404 없음/타인, 409 상태·중복·AI lease, 410 만료 입력, 412 ETag 불일치, 413 본문 초과, 415 MIME, 422 스키마·파일·수학 검증, 428 조건 헤더 누락, 429 호출 제한, 503 저장소·제공자 장애입니다. Retry-After를 따르고 토큰 실패는 한 번 refresh 또는 재로그인합니다. 커서 필터 변경은 첫 페이지부터 다시 조회합니다.

요청 제한은 영속 고정 분 윈도우입니다. 일반 사용자 120/분, 인증 IP 10/분·이메일 5/분, 업로드 URL 20/분, AI 접수 10/분, job별 poll 20/분, worker 600/분입니다. 실패 응답도 카운트하며 동시 작업은 사용자 최대 3개/대상 재구성 1개입니다.

정적 계약과 HTTP 통합 테스트, 실제 SQLite/JPEG/PNG16/PLY/GLB 바이트, 소유권·동시 중복·ETag·lease·과거 버전·삭제·참조·개인 상태를 확인합니다. OAuth는 테스트 RSA 서명과 제공자 모의 응답으로 검증하며 실제 콘솔·SDK 로그인은 미실행입니다. AI팀 형식 확정·실제 기기 RoomPlan 파일·Unity 렌더러·복원 품질·Docker/원격 CI는 별도 통합 확인이 필요합니다. 최종 실행 내역은 검증결과.md와 verification.json에 있습니다.

## 10. 앱 연동 순서·이관

1. 이메일/카카오/구글 로그인과 refresh 회전·토큰 보관을 연결합니다.
2. 금액 원↔만원, location 객체, roomType과 13옵션, owner 표시·상세 주소 권한을 맞춥니다.
3. AssetRef.url로 표시하고 만료/403이면 download API로 재발급합니다.
4. 업로드 세션과 파일 PUT/complete, clientFileId 연결, 카메라 열 우선·마이크로초·바닥 원점 정규화를 구현합니다.
5. 완성 공간·사진 검토 뒤 publication 버튼, 객체 분류·개인 입주 상태를 연결합니다.
6. 채팅 6 API·읽음·3~5초 폴링, 찜 PUT204, 신고201/중복200, 인증 신청·운영 승인을 연결합니다.
7. quaternion과 spaceVersion/modelVersion·ETag를 보관하고 inputSha256은 선택으로 보냅니다.

서버 첫 실행에서 이전 역할과 매물 JSON을 원자 이관합니다. 원 금액·주소 객체·3D 파일 바이트는 유지하고 ownerId/roomType으로 변경합니다. 이전 VILLA/APARTMENT는 방 수 확인 전 DRAFT로 옮깁니다. 실행 전 CLI backup으로 DB와 objects·비밀키를 함께 보존하고 롤백은 해당 백업을 복구합니다. 자동 API 별칭은 없습니다.
